# Contributing to polypath

Welcome. This repo holds the infrastructure, config generator, and research for a
multi-layered anti-censorship VPN stack.

**You need nothing from anyone to start.** No server access, no credentials, no
introductions:

```bash
git clone https://github.com/sep-lab/polypath && cd polypath
npm ci && npm run demo    # generates real configs from fictional servers
npm test                  # 307 tests, no network access
```

That is the whole setup. Everything below is detail.

## Get oriented in 15 minutes

Read in this order — each one explains why the next matters:

1. **[README](./README.md)** — what this is and the shape of it
2. **[docs/threat-model.md](./docs/threat-model.md)** — the adversary, and what
   this explicitly does *not* defend against. Read this before proposing a
   protocol change; it will save you designing against the wrong threat.
3. **[architecture.md](./architecture.md)** — how the layers fit together
4. **[docs/adr/](./docs/adr/)** — 11 decisions with their trade-offs, including
   ones that were reversed

## The one idea everything rests on

No single transport survives indefinitely. A censor eventually recognises any
protocol you deploy. So this project optimises for **the rate at which you can
add and rotate paths**, not for the quality of any one path.

That is why the topology lives in schema-validated YAML rather than in code, why
secrets are referenced by env-var *name* rather than value, and why negative
results — which protocols stopped working, and how they were detected — are kept
in the repo instead of deleted.

## What to work on

The most valuable contribution is usually a **measurement**: which transport
survives on which network, and the method you used to find out. Second most
valuable is a protocol or evasion technique with a citation.

- [`good first issue`](https://github.com/sep-lab/polypath/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22) — self-contained, no infrastructure needed
- [`help wanted`](https://github.com/sep-lab/polypath/issues?q=is%3Aissue+is%3Aopen+label%3A%22help+wanted%22) — larger research pieces

### Safety when contributing measurements

This tracker is public. **Do not post from an account you would not want linked to
circumvention work, and do not include your IP, ISP, city, or working configs in
an issue.** If you are on a censored network, share results in whatever form and
through whatever channel you are comfortable with — an unattributed summary is
more useful than nothing, and far better than a deanonymised detailed report.

Do not volunteer publicly to run tests from inside a censored country. Replying
"I'm in X, I can test" self-identifies you.

## Getting Started

### 1. Clone & Set Up

```bash
git clone git@github.com:<YOUR-ORG>/polypath.git
cd polypath

# Install Node.js dependencies
npm install

# Build: generates constants from config/*.yaml and bundles TypeScript
npm run build

# Run tests
npm test

# Optional: decrypt production secrets (maintainers only — not needed to contribute)
# sops config/secrets/servers.enc.yaml
```

### 2. Read the Docs (in this order)

1. [architecture.md](./architecture.md) — understand the protocol stack & 5 layers
2. [multi-server.md](./multi-server.md) — current 4-server inventory
3. [strategy-roadmap.md](./strategy-roadmap.md) — where we're headed (especially Track 8: IP Hiding)
4. [checklist.md](./docs/ops/checklist.md) — how a fresh server gets deployed end-to-end

### 3. Local Development (Smart-Sub Worker)

The smart-sub worker is a Cloudflare Pages Function that generates VPN subscription configs.

```bash
# Navigate to the worker
cd tools/smart-sub

# Install dependencies (vitest for tests)
npm install

# Set up local secrets for wrangler dev
# For your own deployment, copy .dev.vars.example and fill in your values.
# To just run things locally, use the committed demo fixture: npm run demo
# .dev.vars contains all 21 env vars (UUIDs, server IPs, passwords)
# This file is gitignored — never commit it

# Start local dev server
npx wrangler dev worker.js --port 8787
```

Test it:

```bash
# Health check — should show 4 servers, all protocols
curl http://localhost:8787/health | python3 -m json.tool

# Subscription endpoint (use test UUID from .dev.vars)
curl http://localhost:8787/sub/<TEST_UUID>

# Decoded output — should show ~190 configs
curl -s http://localhost:8787/sub/<TEST_UUID> | base64 -d | head -20

# Run unit tests
npx vitest run
```

### 4. Deploying (Ansible)

Server configuration is managed via Ansible playbooks in `infra/ansible/`.
The legacy `tools/deploy/*.sh` scripts are deprecated.

```bash
# Full server setup (first time or complete refresh)
ansible-playbook infra/ansible/playbooks/site.yml \
  -i infra/ansible/inventory/hosts.yml

# Protocol-only update (skip system config changes)
ansible-playbook infra/ansible/playbooks/protocols.yml \
  -i infra/ansible/inventory/hosts.yml

# Upgrade Docker images to latest
ansible-playbook infra/ansible/playbooks/upgrade.yml \
  -i infra/ansible/inventory/hosts.yml

# Or push to main — GitHub Actions deploys automatically
# (requires 'production' environment approval)
```

See `infra/ansible/` for the complete role structure and `infra/ansible/inventory/group_vars/`
for per-server protocol flags.

### 5. Adding a Protocol

1. Add TypeScript interface in `tools/smart-sub/src/types.ts`
2. Add `generateNewProtocolURI()` function in `tools/smart-sub/src/generators.ts`
3. Add protocol config to `config/servers.yaml` (source of truth)
4. Update `tools/smart-sub/src/config.ts` to map the new field
5. Call the generator in `tools/smart-sub/src/index.ts`
6. Run `npm run build` to regenerate `worker.js`
7. Add an Ansible role in `infra/ansible/roles/` if it requires server-side config
8. Test with `npx wrangler dev worker.js --port 8787`

### 6. Server Access

Contributors run this playbook on their **own** servers. Nobody hands out access to
this project's fleet, and you should not accept SSH access to anyone else's machine
(see the threat model, §3.6). A server you provision yourself runs:

- **sing-box** (Reality + Hysteria2 + WS) via Docker Compose
- **xray-core** (XHTTP + TCP-HTTP + SS2022) via Docker Compose
- **HAProxy** on port 443 routing to all internal services
- Various protocol containers (see [architecture.md](./architecture.md))

```bash
# SSH into YOUR OWN server (the one you provisioned)
ssh root@<YOUR_SERVER_IP>

# Check running services
docker ps
systemctl status haproxy

# View logs
docker compose logs -f --tail=50
```

### 6. Deploying Worker Changes to Production

After testing locally, deploy to Cloudflare Pages:

```bash
cd tools/smart-sub

# Option A: Use npm script (recommended — runs tests first)
npm run deploy

# Option B: Manual deploy
mkdir -p /tmp/vpn-sub-deploy && cp worker.js /tmp/vpn-sub-deploy/_worker.js
npx wrangler pages deploy /tmp/vpn-sub-deploy --project-name your-pages-project --commit-dirty=true

# Option C: Push to main — automated deploy triggers via GitHub Actions
git push origin main
```

Verify production:

```bash
curl https://sub.example.com/health | python3 -m json.tool
```

> **Note**: Only deploy to production after PR is merged and admin approves.

## Working with AI (Claude / Copilot)

This project is set up for AI-assisted development. Here's how to use it effectively.

### Claude Code (Recommended)

[Claude Code](https://docs.anthropic.com/en/docs/claude-code) is a CLI tool that understands the full project context.

```bash
# Install
brew install claude

# Start in the project root
cd polypath
claude
```

The repo includes a `.claude/CLAUDE.md` file that automatically loads project context into Claude — it knows the architecture, server inventory, protocols, and conventions.

**What Claude Code is great for:**

- Reading and understanding spec files across the project
- Writing deploy scripts that follow existing patterns
- Modifying `worker.js` (config generators, new protocols, account management)
- Updating documentation consistently across multiple files
- Debugging server issues by analyzing logs
- Git operations (branching, PRs, commits with good messages)

**Example workflows:**

```text
> "Add TUIC v5 protocol support to worker.js"
> "Write a deploy script for Gcore CDN relay following deploy-xhttp.sh pattern"
> "Update all spec files to reflect the new server in Tokyo"
> "Check which protocols are missing from the Helsinki server config"
```

### GitHub Copilot (VS Code)

If using VS Code, install the [GitHub Copilot extension](https://marketplace.visualstudio.com/items?itemName=GitHub.copilot). It provides:

- Inline code completion for shell scripts and JavaScript
- Chat panel for questions about the codebase
- `@workspace` for project-wide context

### Tips for AI-Assisted Work

1. **Always work on a branch** — AI can make sweeping changes, review them via PR before merging
2. **Test after AI edits** — run `wrangler dev` locally and verify `/health` + `/sub/<test-uuid>`
3. **Check diffs carefully** — `git diff` before committing, especially for `worker.js` (UUIDs, server IPs)
4. **Use conventional commits** — AI tools generate better commit messages when you follow the format
5. **The `.claude/CLAUDE.md` is your friend** — update it when architecture changes so AI stays current

## Workflow

### Branch & PR Model

We use a **trunk-based** model with short-lived feature branches:

```text
main (protected — requires PR + approval)
  ├── feature/add-tuic-protocol
  ├── fix/hysteria2-reconnect
  ├── docs/update-client-setup
  └── infra/ip-rotation-script
```

### Branch Naming

| Prefix | Use For | Example |
|---|---|---|
| `feature/` | New protocols, worker features, tools | `feature/gcore-cdn-relay` |
| `fix/` | Bug fixes, config corrections | `fix/salamander-port-range` |
| `docs/` | Documentation updates | `docs/add-arvancloud-guide` |
| `infra/` | Server provisioning, deployment scripts | `infra/hetzner-ip-rotation` |
| `research/` | DPI analysis, protocol testing | `research/iran-quic-blocking` |

### Making Changes

1. **Create a branch** from `main`:

   ```bash
   git checkout main && git pull
   git checkout -b feature/your-feature-name
   ```

2. **Make your changes** — keep commits focused and atomic

3. **Test locally** if touching worker.js:

   ```bash
   cd tools/smart-sub
   npx wrangler dev worker.js --port 8787
   # verify /health and /sub/<test-uuid> work
   ```

4. **Push & open a PR**:

   ```bash
   git push -u origin feature/your-feature-name
   gh pr create --title "Add TUIC v5 protocol" --body "Adds TUIC v5 support to..."
   ```

5. **Get a review** — at least one approval required before merging

6. **Merge** — use squash merge for clean history

### Commit Messages

Use conventional-ish format:

```text
feat: add TUIC v5 protocol support
fix: correct Salamander port range in deploy script  
docs: update client-setup for new protocols
infra: add Hetzner IP rotation script
chore: update .gitignore, clean wrangler artifacts
```

## Sensitive Data

### ⚠️ Security Rules

- **NEVER** commit real credentials, keys, or tokens to this repo
- Server IPs and UUIDs in spec files are for documentation only — the actual deployed configs live on the servers
- `vars.env` is gitignored — never commit it
- `.dev.vars` is gitignored — contains all 21 Wrangler env vars for local `worker.js` development
- Since v4.1.0, all secrets are externalized from `worker.js` into env vars via `buildConfig(env)` — no UUIDs or passwords in source code
- API tokens, SSH keys and passwords are never shared through this repo, and never in PRs

### What's OK to Commit

- Documentation, guides, diagrams
- Deploy scripts (with placeholder values)
- Worker.js changes (but UUIDs/account changes need admin review)
- Protocol configuration templates
- Research notes and analysis

## Testing Checklist

Before opening a PR, verify:

- [ ] `worker.js` changes: tested locally with `wrangler dev` — `/health` returns all servers, `/sub/<test-uuid>` returns valid configs
- [ ] `worker.js` changes: `npx vitest run` passes the full test suite
- [ ] Deploy scripts: tested on a fresh VPS (or at minimum, syntax-checked with `bash -n script.sh`)
- [ ] Documentation: links work, no broken references, placeholder format (`<PLACEHOLDER>`) used for secrets
- [ ] No secrets or real credentials in the diff

## Server Access & Credentials

### Getting Access

This project is self-hosted: you run the stack on **your own** infrastructure. There is
no shared fleet to be granted access to — do not ask for, or accept, SSH access to anyone
else's machine (see the threat model, §3.6).

1. **Provision your own server** — see [docs/guides/quickstart.md](./docs/guides/quickstart.md)
2. Add your **own** SSH key to your **own** server
3. Generate your own per-server credentials — never reuse values from this repo

### What You Need

| Credential | Where It Lives | How to Get |
|---|---|---|
| **SSH key** (ed25519) | Your machine | `ssh-keygen -t ed25519 -C "your@email.com"` — add the `.pub` to your own server |
| **Server IP** | Your provider's dashboard | The IP of the server you provisioned |
| **UUID** | Generate with `uuidgen` | Never commit |
| **Wrangler auth** | Your machine | `npx wrangler login` — authenticates with your own CF account (dev only) |
| **vars.env** | Your machine | Copy from `tools/deploy/vars.env.example`, admin fills in secrets |

### GitHub Repository Secrets

For CI/CD workflows that interact with production, the admin configures these in **Settings → Secrets and variables → Actions**:

| Secret Name | Purpose | Who Sets It |
|---|---|---|
| `CF_API_TOKEN` | Deploy worker.js to CF Pages (future CD pipeline) | Admin |
| `CF_ACCOUNT_ID` | Cloudflare account identifier | Admin |
| `SSH_PRIVATE_KEY` | SSH into servers for automated deploys (future) | Admin |
| `TELEGRAM_BOT_TOKEN` | Health monitoring alerts (future) | Admin |
| `TELEGRAM_CHAT_ID` | Alert destination chat (future) | Admin |

> **Note**: These secrets are only needed for automated deployment pipelines. For local development, you only need Wrangler login and SSH access.
