# Release Process

This document defines the step-by-step process for cutting a release. Follow it exactly; CI will enforce most of these rules automatically.

## Version Sources (must all agree)

| Source | Location | Format |
|---|---|---|
| `worker.js` header | `tools/smart-sub/worker.js` line 1 | Generated by `npm run build` |
| `worker_version` field | `tools/smart-sub/src/index.ts` (in /health response) | `"5.11.0"` |
| `package.json` | `tools/smart-sub/package.json` `"version"` | `"5.11.0"` |
| `CHANGELOG.md` | `## [5.11.0] - YYYY-MM-DD` | `[5.11.0]` |

The `ci.yml` doc-sync job verifies doc files reference the current short version (`v5.11`). Release-please (`release.yml`) auto-bumps `package.json` (root + smart-sub), `worker_version` in `index.ts` (via `x-release-please-version` annotation), and creates CHANGELOG entries on merge to `main`.

## Who Can Release

- **Admin** has direct push + deploy access
- **Contributors** open a PR → admin merges → automated deploy triggers on push to `main`
- **Manual releases** can be triggered via GitHub Actions → "Release — Tag & Publish" → Run workflow

## Step-by-Step: Cutting a Release

### 1. Bump version numbers

Release-please handles most version bumps automatically (root `package.json`, `tools/smart-sub/package.json`, and `worker_version` in `src/index.ts`). If doing a manual release, update these files **in one commit**:

```bash
# 1. worker_version in src/index.ts (search for x-release-please-version)
# Change: worker_version: "X.Y.Z", // x-release-please-version
# To:     worker_version: "X.Y+1.Z", // x-release-please-version

# 2. package.json (root + tools/smart-sub)
# Change: "version": "X.Y.Z"
# To:     "version": "X.Y+1.Z"

# 3. Rebuild the worker
npm run build

# 4. Verify versions match
cd tools/smart-sub && npm run version:check
```

### 2. Update CHANGELOG.md

Add a new section at the top of CHANGELOG.md:

```markdown
## [5.10.0] - 2026-MM-DD

### Added
- ...

### Changed
- ...

### Fixed
- ...
```

### 3. Update documentation refs

The `ci.yml` doc-sync job will fail if these files reference the old version:

- README.md
- architecture.md
- strategy-roadmap.md
- docs/ops/checklist.md
- docs/guides/client-setup.md
- CONTRIBUTING.md
- docs/api.md
- .claude/CLAUDE.md

Update version references (e.g., `v5.11` → `v5.12`) in all of them. These are prose references that release-please cannot auto-bump.

### 4. Build and test

```bash
npm run build    # Bundles src/ → worker.js + core-worker.js
npm test         # All unit + integration + config-count tests
```

### 5. Commit and push

```bash
git add -A
git commit -m "release: v5.12.0 — <one-line summary>"
git push origin main
```

This triggers:

- **CI** → lint + quality checks
- **Tests** → unit + smoke tests
- **Doc Sync** → version consistency
- **Deploy** → builds from `src/`, deploys to CF Pages + Vercel

### 6. Tag and release

#### Option A: Manual tag (recommended)

```bash
git tag -a v5.10.0 -m "Release v5.10.0"
git push origin v5.10.0
```

This triggers the `release.yml` workflow which auto-creates the GitHub Release with notes from CHANGELOG.md.

#### Option B: GitHub Actions dispatch

1. Go to Actions → "Release — Tag & Publish"
2. Click "Run workflow"
3. Enter version: `5.10.0`
4. Optionally check "draft" for review before publishing

### 7. Verify

```bash
# Check deployment
curl -s https://sub.example.com/health | python3 -m json.tool
curl -s https://sub.example.net/health | python3 -m json.tool

# Check release page
gh release view v5.10.0
```

## Automated Deployment Flow

```text
Push to main (src/ or config/ changed)
  │
  ├─ test-gate: npm run build → vitest run (must pass)
  │
  ├─ deploy-cf-pages: npm run build → wrangler pages deploy → sub.example.com
  │   └─ health check verification
  │
  └─ deploy-vercel: npm run build → vercel deploy --prod → sub.example.net
      └─ health check verification
```

## Rollback

If a deploy breaks production:

```bash
# 1. Check what's broken
curl -s https://sub.example.com/health | python3 -m json.tool

# 2. Revert to previous commit
git revert HEAD
git push origin main
# This triggers a new deploy with the reverted code

# 3. Or manually deploy a known-good version
git checkout v5.9.0 -- tools/smart-sub/src/
npm run build
mkdir -p /tmp/vpn-sub-deploy
cp tools/smart-sub/worker.js /tmp/vpn-sub-deploy/_worker.js
npx wrangler pages deploy /tmp/vpn-sub-deploy --project-name your-pages-project --commit-dirty=true
```

## GitHub Actions Secrets Required

These must be configured in **Settings → Secrets → Actions** by the admin:

| Secret | Required For | Status |
|---|---|---|
| `CF_API_TOKEN` | CF Pages deploy | Required |
| `CF_ACCOUNT_ID` | CF Pages deploy | Required |
| `VERCEL_TOKEN` | Vercel backup deploy | Required |
| `VERCEL_ORG_ID` | Vercel backup deploy | Required |
| `VERCEL_PROJECT_ID` | Vercel backup deploy | Required |

## Version Bumping Cheat Sheet

| Change Type | Version Bump | Example |
|---|---|---|
| New protocol, major feature | Minor (x.**Y**.0) | 5.9.0 → 5.10.0 |
| Bug fix, config tweak | Patch (x.y.**Z**) | 5.9.0 → 5.9.1 |
| Breaking change (rare) | Major (**X**.0.0) | 5.9.0 → 6.0.0 |
